# Защита репозитория

Репозиторий остаётся публичным: код можно читать и копировать. Право записи
должно быть только у владельца. Публичность не даёт посетителям доступ к secrets
или разрешение публиковать изменения на сервере.

`main` защищён обязательным PR и успешным `Validate site`; force push и удаление
ветки запрещены, в том числе администраторам. Увеличивать число обязательных
одобрений до одного при единственном владельце нельзя без второго доверенного
ревьюера: GitHub не позволяет автору одобрить собственный PR.

Workflow использует GITHUB_TOKEN только для чтения и не сохраняет его в Git.
Все внешние Actions закреплены на полном commit SHA. Публикация допускается
только из исходного репозитория, ветки main и событий push/workflow_dispatch;
SSH-скрипт повторно проверяет эти условия до использования ключа.

Не добавлять `pull_request_target` с выполнением кода из внешнего PR. Не
передавать SSH secrets в jobs проверок, артефакты, комментарии или логи. Перед
одобрением запуска чужого PR просматривать изменения workflow и скриптов.

Secrets пока хранятся на уровне репозитория. Для более строгого ограничения
доступа можно заново сохранить четыре SERVER_* secrets в environment production,
проверить preflight, затем удалить repository-копии. GitHub не позволяет прочитать
значения существующих secrets, поэтому автоматического переноса без исходного
ключа нет. Ограничение production должно разрешать только ветку main.

Включить двухфакторную аутентификацию аккаунта и сохранить recovery codes
вне репозитория. Периодически проверять доступы приложений и срок действия токенов;
не отзывать используемое подключение GitHub до подготовки замены.

SSH-ключ должен быть отдельным ключом для пользователя deploy без прав sudo.
При реальной утечке отозвать соответствующий публичный ключ на сервере и заменить
SERVER_SSH_KEY в GitHub. Удаление файла из последнего коммита не убирает его из
истории и не заменяет ротацию ключа.

Сервер, системный nginx, VPN и decoy не меняются при настройке защиты GitHub.
