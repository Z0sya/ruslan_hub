# Публикация сайта без изменения VPN

## Текущий способ запуска

Порт 8080 уже занят, а у deploy нет прав на системный nginx. Для нового сайта
используется отдельный nginx на **8081**, запускаемый самим deploy. Его конфигурация,
PID, логи и временные файлы находятся в `/var/www/main-site/.nginx`; корень сайта —
`/var/www/main-site/current`. Системные nginx-конфиги не меняются и основной nginx
не перезагружается. Скрипт откажется занимать уже используемый порт или заменять
неизвестную конфигурацию/чужой процесс.

При наличии работающей службы cron добавляется одна запись `@reboot` только в
crontab пользователя deploy, сохраняя все его прежние записи. Если cron недоступен,
это явно видно в логе: после перезагрузки серверу потребуется новый запуск deploy.
Адрес сайта: `http://31.56.48.8:8081`. Если внешний доступ блокирует firewall,
администратору потребуется открыть TCP 8081. Workflow не меняет firewall.

Для этого способа нижеприведённый пример отдельного системного virtual host
применять не нужно; он оставлен как вариант будущего переноса под администратора.

## Что подготовлено

Один workflow `CI and deploy`: PR → проверки → архив; `main` → те же проверки →
деплой, если владелец включил `DEPLOY_ENABLED=true`. `needs: ci` запрещает
публикацию при ошибке проверок. PR не получает SSH secrets. Actions закреплены
на commit SHA, Dependabot проверяет обновления еженедельно.

Схема файлов сервера:

```text
/var/www/decoy/                         существующий сайт/VPN, не изменяется
/var/www/main-site/
  releases/<commit>-<run>-<attempt>/    отдельная версия сайта
  current -> releases/<...>/           атомарно переключаемый указатель
  .deploy.lock                        блокировка параллельной выкладки
```

Нет `sudo`, `rsync --delete`, перезагрузки nginx и автоматического удаления старых
версий. Прежние файлы непосредственно в `main-site` также не удаляются.
Распаковка запрещает ссылки и выход из каталога, проверяет SHA256 и commit SHA.
На сервере используется `flock`; GitHub сериализует публикации без отмены работающей
выкладки. Устаревший запуск пропускается, если `main` уже сменился до загрузки.

## Что должен проверить владелец сервера перед включением

1. Войти по SSH именно под `deploy`. `/var/www/main-site` должен быть реальной
   папкой, доступной ему для записи. `current`, если есть, должен ссылаться только
   на каталог внутри `main-site/releases`. Скрипты откажутся заменять обычную папку
   или файл `current`.
2. Убедиться в наличии Bash, Python 3.10+, curl, tar, flock и обычных GNU coreutils.
   Если нужны пакеты/права, администратор настраивает их отдельно; workflow не
   получает права root и не меняет владельцев произвольных файлов.
3. Проверить только виртуальный хост, предназначенный для нового сайта. Его `root`
   должен указывать на `/var/www/main-site/current`, а выбранный домен/порт — на
   этот виртуальный хост. Не менять существующий VPN/decoy server block. Если
   требуется перенастроить nginx, сначала сохранить копию конфигурации, затем
   проверить `nginx -t` и отдельно применить её. В workflow этого нет.
4. Убедиться, что nginx может читать и проходить каталоги `main-site` и `releases`.
   Создаваемые версии имеют права 755 для каталогов и 644 для файлов.

Пример фрагмента внутри НОВОГО, отдельно проверенного `server` block
(это не готовая замена существующего VPN-конфига):

```nginx
root /var/www/main-site/current;
index index.html;
location / { try_files $uri $uri/ /index.html; }
location /assets/ { try_files $uri =404; }
location = /release.txt {
    add_header Cache-Control "no-store" always;
    try_files $uri =404;
}
location = /sw.js {
    add_header Cache-Control "no-cache" always;
    try_files $uri =404;
}
location = /index.html {
    add_header Cache-Control "no-cache" always;
    try_files $uri =404;
}
```

До первой выкладки `current` может отсутствовать: поэтому новый виртуальный хост
может временно отвечать 404. Существующий decoy продолжает работать по прежней
конфигурации. Выбор домена/порта и совместимость с VPN проверяет владелец.

## GitHub secrets и переменные

Settings → Secrets and variables → Actions. Нужны четыре secrets:

| Имя | Содержимое |
| --- | --- |
| SERVER_HOST | Только адрес сервера, без `ssh://`, порта и пользователя |
| SERVER_USER | `deploy` |
| SERVER_SSH_KEY | Отдельный приватный ключ CI без passphrase, целиком с переносами |
| SERVER_KNOWN_HOSTS | Заранее проверенная запись host key для адреса и SSH-порта |

Не копировать приватный ключ в код, PR, логи или чат. Не отключать проверку
host key. При нестандартном порте запись known_hosts должна соответствовать
`[host]:port`. Перед сохранением сверить fingerprint с доверенным источником
на сервере: один `ssh-keyscan` без сверки не подтверждает подлинность хоста.

Переменные Actions (Variables):

| Имя | Значение |
| --- | --- |
| DEPLOY_ENABLED | Пока не создавать или установить `false` |
| SITE_URL | Проверенный адрес нового сайта, например `https://site.example.com`, без query/fragment |
| SERVER_PORT | При необходимости; по умолчанию `22` |

`SITE_URL/release.txt` должен возвращать точный SHA коммита, а `index.html` — HTTP
200. Адрес должен быть доступен с сервера. Кеш/CDN для release.txt нужно отключить.
HTTP без TLS допустим для локального проверочного адреса; публичный адрес лучше
использовать с HTTPS. TLS-проверка не отключается.

Environment `production` создан и ограничен веткой `main`. При желании
добавить required reviewer. Environment само по себе не включает защиту — правила
нужно настроить явно. SSH secrets могут находиться в repository secrets или в
`production`; environment secrets с теми же именами имеют приоритет.

Защита `main` должна требовать PR, успешный check **Validate site** и актуальность
проверенной ветки. Результат настройки указан в описании PR; проверить его перед
слиянием. Настройка ссылается на реальный check после первого CI.

## Первый запуск

1. Просмотреть PR и дождаться зелёного `Validate site`, затем влить его в `main`.
   Само слияние при выключенном `DEPLOY_ENABLED` сайт не публикует.
2. Actions → CI and deploy → Run workflow → ветка `main`, режим `preflight`.
   Этот режим проверяет наличие четырёх secrets, формат ключа, SSH под `deploy`,
   нужные инструменты и безопасность каталога. Не создаёт файлы на сервере,
   не публикует сайт и не читает конфигурацию VPN. Ожидаемый маркер: `PREFLIGHT_OK`.
3. Проверить nginx/права и `SITE_URL` по разделам выше. Только затем поставить
   `DEPLOY_ENABLED=true` и вручную запустить режим `deploy` на `main`.
4. Ожидаемые маркеры: `PREFLIGHT_OK`, затем `DEPLOY_OK: <SHA>`. Открыть сайт и
   проверить, что VPN и decoy работают как прежде. Следующие изменения `main`
   будут публиковаться автоматически после успешного CI.

Проверка secrets сообщает только факт наличия, а не значения. Отсутствие одного
останавливает job с его именем. `Permission denied (publickey)` означает, что
ключ Actions не принят пользователем deploy. `Host key verification failed`
требует сверки записи known_hosts, а не отключения проверки.

## Откат и остановка

При ошибке HTTP-проверки или обычном прерывании скрипт возвращает прежний `current`.
Если это первая выкладка и прежнего `current` не было, новый указатель удаляется;
старые файлы не трогаются. Версии сохраняются для расследования/ручного отката.
SIGKILL, отключение питания и потеря сервера не позволяют гарантировать выполнение
обработчика: в таких случаях проверить `current` вручную перед повтором.

Чтобы остановить будущие выкладки: установить `DEPLOY_ENABLED=false`. Для отката
к старому содержимому через CI — revert нужного коммита в отдельном PR и слияние
после проверок. Если нужен аварийный ручной откат, после отключения автодеплоя
выбрать реальный предыдущий каталог и атомарно заменить ссылку под серверной
блокировкой. Не удалять папки версий, на которые ссылается `current`.

Уже открытые вкладки/PWA могут использовать кеш прежней сборки и запрашивать
старые JS-модули. После выкладки проверить обновление и офлайн-режим отдельно;
при необходимости пользователю потребуется перезагрузка. Получив настоящие
исходники, стоит добавить воспроизводимую сборку с lockfile и браузерные тесты.
